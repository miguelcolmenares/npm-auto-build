### Each architecture rule, broken on purpose

We copied the repository to a scratch directory, added one line that breaks the rule, and ran the matching test file. The control copy (no change) had 0 failures.

| Rule from #11 | Line we added to the scratch copy | Test that failed |
|---|---|---|
| The install and build scripts never read the token | `echo "$GITHUB_TOKEN"` in `install.sh`, `${NAB_TOKEN:-}` in `build.sh`, `$GH_TOKEN` in `check.sh` | "install.sh and build.sh never read a token variable" (2 cases), "only the scripts on the token allowlist read a token variable" (1 case) |
| Only the commit script pushes | `git push` in `check.sh` and in `build.sh`, `git fetch` in `validate-inputs.sh` | "only the token scripts push to or fetch from a remote" (3 cases) |
| No network except the package manager | `curl` in `install.sh`, `gh api` in `build.sh`, `wget` in `commit.sh`, `/dev/tcp` in `lib.sh` | "no script calls a network tool, the package manager is the only way out" (4 cases) |
| Every script starts with `set -euo pipefail` | `-u` removed from `build.sh`, the line removed from `pr.sh`, `set +e` and `set +o pipefail` added | "every script starts with the shebang and set -euo pipefail" (2 cases), "no script turns off errexit, nounset or pipefail" (2 cases) |
| Nothing written outside the workspace and the temporary directory | `> "$HOME/.bashrc"`, `> /etc/...`, `npm install -g`, `git config --global` | "no script installs a tool for the whole machine or touches a system or home path" (4 cases) |

## Residual risk accepted

**Proposed,** until the maintainer confirms:

- **One maintainer.** Nobody else reads a change before it merges (F8, F16). The required checks and the 337 tests reduce the risk. A second maintainer would close it.
- **Same-repository pull requests run project code with the workflow token** in v2. v3 removes the token from install and build. The exception is a checkout that keeps its credentials (F3).
- **Third-party actions and the runner image.** They are pinned by SHA or by the runner version, and we did not read their code.
- **Text-based tests.** The architecture tests search for names. They cannot see `${!name}` or a command built from pieces. This is stated in `docs/architecture.md`.
- **`@v2` is a moving tag.** Users who follow it get any change that moves it (threat T4).

## Repeat before each major release

Run this audit again before v3.0.0, and before each later major release.

1. Run `shellcheck`, `actionlint`, `zizmor` and `bats tests/`. Record the counts.
2. Break each architecture rule on a scratch copy and record the failing test. Add one new break for each rule that changed.
3. Read the branch protection, the security settings and the code scanning alerts with `gh api`. Record the numbers.
4. Check that every `uses:` is a 40 character SHA and every workflow has `permissions:`.
5. Check that every checkbox in the release issue has a file or a command as evidence.
6. Run the F3 demo again, and read the code of `git-lib.sh`, `commit.sh` and `pr.sh` line by line.

## Decisions for the maintainer

Decisions 1, 2, 3, 6 and 7 were answered on 2026-11-12, and the findings table says how. Decision 4 is done for F9, and F5 still needs the registration at bestpractices.dev. Decision 5 (accepted risks) is not confirmed yet.

1. **v2 image (F1).** Recommended: cut a `v2` maintenance branch at tag `v2.1.2`. Move the base image to a current LTS version pinned by digest, add Trivy there, and release v2.1.3. One release reaches every `@v2` user, because the tag moves. The cost is one branch to keep until the sunset. The other option is to end v2 support at the v3.0.0 release and change `SECURITY.md` to say that v2 gets no patches. Both options need a release or a policy change, which #11 may not make.
2. **Sunset date (F2).** Pick a date, for example a fixed number of days after v3.0.0, and write it in `SECURITY.md`.
3. **Persisted credentials (F3).** Approve the follow-up: check before install, fail in modes commit and pr.
4. **Settings (F5, F9).** Register at bestpractices.dev. Turn on "Require actions to be pinned to a full-length commit SHA".
5. **Accepted risks (F8, F14, F15, F16, F17).** Confirm them, or ask for a change.
6. **Security update merge time (F10).** Confirm 7 and 30 days, or give other numbers.
7. **Recurring audit (F11).** Approve the issue text above, and say who creates it.
